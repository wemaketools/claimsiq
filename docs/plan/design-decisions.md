# Design decisions

The decision log of the ClaimsIQ build. The product specifications in `ai/specs/` come first; this log records how they were turned into build decisions and amends the technical documents. A decision is never edited away: a changed decision is a new entry that says which one it replaces.

Format: `DD-nn`, the decision, then why.

## Scaffold (Stage A, item 1)

### DD-01 Standalone repository shaped like TenderIQ

ClaimsIQ is its own repository with the layout of the TenderIQ repository: `src/ui` (SPA), `src/server` (platform modules), `scripts`, `supabase`, `e2e_tests`, `docs`. The parts the specs want shared with the other products (contracts, fixtures and loader, rules, shell) get clearly separate folders, so they can move into a shared package once the link to Premium Collections is settled.

Why: the owner chose one codebase per product that reads as one suite; separate folders keep a later extraction cheap.

### DD-02 Same tool versions as TenderIQ

TypeScript ~6, Vite 8, React 18.3, Redux Toolkit 2, React Router 7, recharts 3, zod 4, Hono, Kysely, supabase-js 2, the Supabase CLI as a devDependency, Vitest with React Testing Library, Playwright in `e2e_tests`. Bun workspaces (DD-13): the UI is `src/ui` (package `@claimsiq/ui`), the Playwright suite is `e2e_tests` (`@claimsiq/e2e`). Hono, Kysely and `pg` are declared for the backend that comes later and are not imported yet (Kysely and `pg` are used from DD-49).

Why: a developer or agent who knows one product knows all three; versions move together.

### DD-03 Prefix `ciq`, palette unchanged

Every `--tiq-*` token and `.tiq-*` class of the TenderIQ design system is `--ciq-*` / `.ciq-*` in ClaimsIQ. Every palette hex value is kept, including the AA-contrast `-text`, `accent-fill` and `on-solid` tokens. Components contain no raw hex values and no literal pixel gaps.

Why: the three products must read as one suite; only the prefix identifies the product. Keeping the AA tokens keeps the contrast guarantees.

### DD-04 Brand

The wordmark is `Claims` plus the accent `IQ` (`Claims<span class="ciq-brand-iq">IQ</span>`), the sub-brand is "Claims Intelligence", the collapsed rail shows `C` plus `IQ`. The favicon is a rounded square `#10808a` with a white "C", in the style of the TenderIQ favicon. The document title is `{page} · ClaimsIQ`.

### DD-05 What was copied and what was left out

Kept, because it is generic: the theme (tokens, components, global CSS), the `components/ui` library, the charts, the shell (AppShell, Sidebar, Topbar, UserCard), authentication (the auth providers, sign-in, forgot and reset password, the demo-accounts list, development-only then and a server-side sign-in since DD-48; since then a prototype mode with its own provider, DD-45 to DD-47), the app store, the route guard, the feature registry, the API client that sends `X-Tenant-Id`, the i18n file, the CSP meta tag, the self-hosted fonts with their OFL licences, `src/server/lib/{config,supabase,auth}`, the CI workflow and `scripts/ci`.

Left out: every tender-specific feature, route, contract, fixture and shared widget (approvals, documents, audit), the public portal and organization selection, the mock API server and the OpenAPI generator. Money formatting from decimal strings and the contracts-driven enum labels are not copied; they come back with the data layer.

### DD-06 Navigation: six destinations (a seventh, Rules, came with DD-61, an eighth, Digest, with DD-63)

The sidebar has, in this order: Overview (`/overview`), Stages & Aging (`/stages`), Exceptions & SLA (`/exceptions`), Claims (`/claims`), Suppliers (`/suppliers`), Action Queue (`/actions`), from DD-61 Rules (`/rules`) as a seventh, and from DD-63 Digest (`/digest`, between Action Queue and Rules) as an eighth. They map to CLM-01, CLM-02, CLM-03, the claims list with CLM-04 (Claim Detail) under it, CLM-05 and CLM-06 of the requirements. `/` goes to the first destination. The sidebar is a flat list (no collapsible sections, no badges, no section actions): eight items do not need them.

Each destination is a feature module (`src/ui/src/features/<feature>`). Until the data layer exists, a page shows its title and one of three states through `useScreenStatus` and `ScreenStates`: loading, then an empty state, or an error state with retry when its loader fails. The screens that follow replace the page body with real content and drop the placeholder. Replaced in part by DD-44: the last placeholder screens were built and `useScreenStatus`, `ScreenStates` and `configureScreenLoader` are deleted; every screen now shows its states through `useApiQuery`, `DataTable` and `QueryView`.

### DD-07 Persona switch is a view, stored in the browser

The persona switch offers Head of Claims, Claims Handler, Supplier Coordinator and Finance (CL §4). It is a **view** switch shown in the top bar ("Viewing as") and in the user card; it is not authentication and does not change what the signed-in account may do (SF §7). The choice is stored in `localStorage` (`ciq.persona`) and read when the store is created, so it survives a refresh. An unknown stored value is ignored and the default, Head of Claims, applies. The light/dark theme is handled the same way (`ciq.theme`).

### DD-08 Real sign-in against local Supabase; one demo account per persona

Sign-in uses real Supabase Auth from the first item. `auth:personas` creates four accounts (`head.of.claims@`, `claims.handler@`, `supplier.coordinator@`, `finance@claimsiq.local`, password `test1234`, local only; the script refuses to run against anything but the local stack). The sign-in page lists the same accounts: the seed script and the page both import the one list in `src/contracts/demoAccounts.ts`, and a SPA test checks that its names are the four persona labels. Amended by DD-48: the page's card signs in through the server and no password is in the SPA; the password here is the local fallback of `DEMO_SEED_PASSWORD`.

Which account you sign in with does not choose the persona (DD-07).

### DD-09 Local stack beside TenderIQ's

`supabase/config.toml` uses project id `claimsiq` and the Supabase CLI default ports plus 100 (API 54421, Postgres 54422, Studio 54423, Mailpit 54424, SMTP 54425), so both products' stacks can run on one machine. The dev server uses 5273 and preview 4273, Playwright 5380.

### DD-10 One demo tenant

The shell labels the dataset with the fixture tenant `DEMO`, "Fictional Botswana insurer demo" (`02_expanded_demo_fixture/tenants.csv`), and the API client sends `X-Tenant-Id: DEMO` on every non-public call while the user is signed in. The name "The Brittany" is not shown in the application chrome (QuoteIQ removed it after review). Tenant switching does not exist yet; the data layer makes the label and the id follow the selected data set (TEST or DEMO).

### DD-11 What the scaffold does not contain

No contracts (`src/contracts`), mock API (`src/mock-api`), fixtures, rules or API functions. They are built by the data layer and rules items. The lint config already guards those folders: `src/contracts` stays pure TypeScript and zod, and `src/server` never imports the mock API.

### DD-12 CI and checks

`.github/workflows/ci.yml` and `scripts/ci/*` mirror TenderIQ's: typecheck, lint, unit tests against the local Supabase stack, SPA tests with a skip check and a test-count floor, build, the secret and bundle scans, and the Playwright suite. The floors are sized to what exists now and are raised when tests are added. `vercel.json` has no `api/` function entries until the backend exists. Replaced in part by DD-13 for the tooling.

### DD-13 Bun, not npm

ClaimsIQ uses Bun as package manager and script runner, unlike TenderIQ, which uses npm, because the owner's environment is Bun-first (QuoteIQ's first PR also used `bun.lock`). Consequences:

- `bun install` with the committed `bun.lock`; no `package-lock.json`. CI and Vercel install with `--frozen-lockfile`. The Bun version is pinned in `.bun-version` (read by `oven-sh/setup-bun`) and in `packageManager`.
- Every package script uses `bun run`, `bun run --filter <workspace> <script>`, `bunx` for CLIs and `bun <file>` for TypeScript and `.mjs` scripts. Nothing calls npm, npx or `node <file>`; `tsx` is gone because Bun runs the files. The `supabase` package is listed in `trustedDependencies` so Bun runs its postinstall, which downloads the CLI binary.
- The test runner stays Vitest (`vitest run`), not `bun test`; Vitest, Vite, ESLint and `tsc` run as their own binaries.
- `.nvmrc` and the Node `engines` entries are removed (this replaces the Node 24 pin of DD-02). Node is not a project requirement; the CI runner's Node, if present, is only what some binary's shebang finds, and Bun supplies a `node` shim when there is none.

## Data layer (Stage A, item 2)

### DD-14 Money uses decimal.js, as strings

Amounts are BWP strings with exactly 2 decimals (`"14000.00"`) in the contracts, the fixtures after loading, and every API answer. Arithmetic goes through `decimal.js` in `src/contracts/money.ts` (`sumMoney`, `addMoney`, `compareMoney`, `normalizeMoney`); a JS number never holds an amount. The CSV amounts without decimals (`14000`) are padded to 2 decimals before validation; anything else that is not a plain non-negative amount is rejected.

Why: SF §5 forbids float sums; `decimal.js` has its own types, rounds half-up by default and is already a transitive dependency of the chart library. The contracts' import rule now allows `decimal.js` beside `zod` (the folder stays pure TypeScript). Replaces the open question in DD-05 about money formatting: formatting from these strings is built with the screens.

### DD-15 Fixtures: versioned CSV folders, the tenant follows the data set

The spec's CSV files live in `fixtures/v1/test` and `fixtures/v1/demo`, next to `expected_metrics.json`, `proposed_rule_config.json` and the README of the spec pack; a changed fixture becomes `fixtures/v2` (DD-65 did this, and `fixtures/v2` is the only copy in the tree). The SPA bundles the CSV text with Vite and the loader (`src/read-model/fixtures`) parses it in the browser. TEST is tenant `TEST` "Fixture validation", DEMO is tenant `DEMO` "Fictional Botswana insurer demo"; the shell takes both from `DATA_SETS` in `src/contracts/datasets.ts` (a test checks they equal `tenants.csv`). The default data set is DEMO. A row whose `tenant_id` is not the data set's tenant is rejected, so the two never mix. Replaces the fixed tenant constant of DD-10.

### DD-16 The mock API runs in the browser behind the client's transport

Stage A has no server. `src/mock-api` implements the typed endpoints of `src/contracts/endpoints.ts` as a `fetch`-shaped function and `src/ui/src/api/mockTransport.ts` hands it to the API client as the `transport` adapter (the platform `fetch` when no transport is installed). The context of a call travels in headers, as it would to a server: `X-Tenant-Id` (the data set's tenant), `X-As-Of` and `X-Persona` (the actor of a command). Answers are `application/problem+json` on failure. The API client keeps validating every answer against the endpoint's schema in development builds, so the mock cannot drift from the contract.

Lint boundaries: `src/mock-api` takes no Node module outside its tests; in the SPA only `src/api/mockTransport.ts` and tests import it. Stage B replaces `mockTransport.ts` with the real `fetch` and nothing else in the SPA. Reads are raw records, except `claims.facts` (DD-22), `claims.paidTrend` (DD-62), `claims.whatIf` (DD-60) and `suppliers.insights` (DD-40), which run the rules engine over them, and the `overdue` flag on each task of `tasks.list` (DD-42).

### DD-17 Validation: reject, warn, never coerce

The loader checks every row against the contracts and keeps a list of data issues `{ file, row, record_id, field, problem, fix }`. A bad row is **quarantined** (left out of the data) for: a value of the wrong form (date, amount, enum, boolean), a missing required field, a tenant other than the data set's, a duplicate id (the first row stays, later ones are rejected), a reference to a parent that is missing or itself rejected (so a rejected claim takes its events with it), a column count that does not match the header, a date before the one it must follow (policy end, due date, report, closure) and an allocation that would over-allocate an invoice or a receipt. A row with **missing evidence** (a claim event without a time, an invoice without a due date, a supplier request without a request time, a claim without a reported date, a closed claim without a closed date) loads with that field `null` and a warning, because the spec says missing evidence is UNKNOWN, never good or bad (SF §5, CL §7). The shell shows the issues under "Data issues (n)".

### DD-18 What "as of" does to a read

Every read takes the as-of date (default 2026-10-21, switchable in the shell and remembered in the browser). A read returns the records whose own date is on or before it: claims by reported date, claim events, reserve events, payments, supplier requests, receipts, allocations and payment attempts by their event dates; a record with an unknown date stays (unknown is not "later"). Values are never rewritten: a claim's `stage`, `status`, `current_outstanding_reserve` and `closed_at` stay as imported, and the rules engine derives the state at the as-of date from the events (CL §7). Not filtered: master data (clients, brokers, products, policies, suppliers, users), invoices (a scheduled instalment whose issue date lies after the as-of date is still a valid due item, and the fixtures hold such invoices) and tasks (workflow records stamped with the real time of the change, not the demo date). A task may only point at a claim that is visible at the as-of date of the request. Every answer says its `tenant_id` and `as_of`.

### DD-19 Changes in browser storage; Reset

What the user changes (tasks and their audit trail, and from DD-61 the saved rule config and its audit) is kept in `localStorage` under `ciq.mock.v1.<data set>.<tenant>`, apart from the fixture, and is merged over it on every read, so a refresh keeps it and the fixture itself is never modified. Reset (a confirm dialog, then `POST /api/v1/demo/reset`) removes the key of the selected data set: the fixture shows exactly as loaded. The data set and the as-of date are views and stay. The mock reads storage on every call, so a second client over the same storage sees the same state (the refresh test relies on it); a failed write answers 507 and the change is not shown as done.

### DD-20 Tasks: shape, actor and audit trail

A task has module (`CLAIMS`, `COLLECTIONS`), subject type (`CLAIM`, `POLICY`, `INVOICE`, `SUPPLIER`) and id, assignee (a user of the tenant or none), due time, priority (`LOW`, `MEDIUM`, `HIGH`), status (`OPEN`, `IN_PROGRESS`, `DONE`), a note and `updated_at`. The endpoints are create, assign and set status; each records an audit entry with the actor (the active persona, from `X-Persona`), the time (Africa/Gaborone, `+02:00`, from the API's clock) and the old and new value. The subject and the assignee must exist in the tenant (422 with the field otherwise). A create carries an `Idempotency-Key`, so a repeated submit returns the same task. Ids are `TASK-0001` and up. The fixtures' `tasks.csv` files are empty, so the statuses and priorities are ours.

### DD-21 Shell controls

The top bar carries the data set switch (TEST, DEMO), the as-of date, "Data issues (n)" (a dialog listing every issue with its file, row, field, problem and fix) and Reset, before the persona switch. Below 1280px the field labels stay for assistive technology only; below 768px the controls wrap onto a second row. Changing the data set clears the screens' filters (the ids differ) and every mounted query reads again.

## Rules engine (Stage A, item 3)

### DD-22 The engine is a pure folder, `src/rules`, and the API serves its facts

`src/rules` holds the claims rules as pure, deterministic functions: `computeClaimFacts` (one claim record, the as-of date, the rule config) and `summarizeClaimFacts` (any list of facts, so a screen can total a filtered subset and never disagree with its list). It imports only `zod`, `decimal.js`, its own files and `src/contracts` (lint-enforced, like the contracts), so Collections and dashboards can reuse it. The shapes of the facts and the summary are contracts (`src/contracts/facts.ts`); the endpoint `claims.facts` (`GET /api/v1/claim-facts`) returns `{ items, summary, breakdowns }` for the as-of view, narrowed by the query of DD-28 and with the period figures of DD-33 and the breakdowns of DD-34, and the mock API runs the engine on the same records `claims.list` returns. The rule config is validated by a zod schema (`src/contracts/ruleConfig.ts`, re-exported by `src/rules/config.ts`) when the mock API is created; an invalid config fails there. Every threshold is read from it. Replaces the sentence of DD-16 that said metrics are not computed by the API.

### DD-23 How days are counted

Claim age is calendar days from the reported date to the as-of date. Stage time and supplier waits are business days: the weekdays named in `business_days` (Monday to Friday in the demo config) strictly after the start date up to and including the as-of date, so a stage entered on a Friday has one business day by Monday evening and none over a weekend (CL §8: "count completed business days at snapshot"). Public holidays are not supported; a config with `holidays_excluded: true` is rejected rather than ignored. Timestamps with a time are reduced to their Africa/Gaborone date for these counts. A stage is breached when business days in stage exceed its target (CL §7: "greater than target"), so being exactly at the target is not a breach. Age buckets are `0-7`, `8-30`, `31-60`, `61-90`, `>90`, built from the upper bounds in the config.

### DD-24 Current stage, open or closed, and the check against the record

The current stage is the `to_stage` of the latest event that has a time (ties on time go to the larger event id); events without a time cannot be ordered and are counted in `undated_events`. A claim is closed when that stage is Closed; a Reopened event makes it open again. With no dated event the recorded status decides and the stage is unknown. Claim records keep the stage, status and reserve as imported (DD-18), which are the state at the config's `as_of` (2026-10-21), so the check `stage_check` / `reserve_check` is `MATCHES` or `DIFFERS` only from that date on, `NOT_COMPARABLE` before it and `UNKNOWN` when there is no event to compare. A `DIFFERS` is the discrepancy alert CL §7 asks for.

### DD-25 Money: paid, reserve, incurred

Paid is the sum of `POSTED` payments dated on or before the as-of date; approved, pending, void and rejected never count. The reserve is the `new_amount` of the latest reserve event at the as-of date, never a sum of events; a claim with no reserve event takes the recorded value. Incurred is paid plus that reserve. The CLM-102 "original estimate P15,000" is the first reserve event; its incurred P17,000 is P5,000 paid plus the current P12,000 reserve (the P2,000 difference is not described as a reserve movement). The first reserve event of a claim, from zero, is `INITIAL` and never material (every claim would otherwise be flagged when opened). A later movement is material when it is at least the absolute threshold, or at least the percent threshold of a positive prior amount (the spec's "or"). Reserve movements are listed for closed claims too, and only open claims enter the severity and the summary counts. A reserve taken to zero while the claim is closed at that moment, such as CLM-103's P4,000 to P0 on 15 Oct, is a `CLOSING_RELEASE`: it stays in the history, shown as "Released on closure", and is never material, so a closed claim carries no review indicator (amended: it was first treated as material by the rule). The same release while the claim is open, including after a reopen, is a movement like any other. A claim is closed at a moment when the latest dated stage event at or before it is Closed; a Closed event with no time stands in as the claim's closed date, unless a later dated event moved the claim on; with no dated event to read, the closed date alone decides (the recorded status decides whether the claim is open at the as-of date), and with neither a zeroed reserve stays a decrease. One helper (`src/rules/closure.ts`) decides this for the releases and for open or closed at the as-of date. The material flag is a review cue; the facts say "reserve change", never leakage.

### DD-26 Missing evidence is unknown

A stage SLA is `unknown` (never `within`) when the claim has no dated stage event, when any of its events has no time (the stage start cannot be trusted), or when the stage has no target in the config (Reopened). A supplier request with no request time is `unverified`, not delayed. A claim is waiting on a supplier when it is open and has a request that is not completed on the as-of date, whatever its stage (the spec does not say which stages wait on suppliers); the target is `supplier_wait_target_business_days`. An open claim without a reported date has no age and is counted in `unknown_age`, apart from the buckets. Closed turnaround needs both the reported and the closed date; closed claims without them are counted in `closed_without_turnaround`.

### DD-27 "Approaching" and severity

CL §7 names "approaching target" without a number. A stage SLA is `approaching` when it is not breached and at most `approaching_window_business_days` (default 1) business days remain. The severity rules also name numbers the spec's config file does not carry, so the engine's config has optional fields with the spec's values as defaults: `severity_high_sla_days_late` (2), `severity_high_reserve_change_min_age_days` (30) and `age_bucket_upper_days` ([7, 30, 60, 90]). An open claim's severity is the highest of its reasons, each with the numbers that triggered it:

| Rule | Severity |
|---|---|
| `SLA_LATE`: breached by more than 2 business days | High |
| `RESERVE_CHANGE_AGED`: material reserve change and age over 30 days | High |
| `HIGH_VALUE_DELAYED`: incurred at or above the high-value threshold and (SLA breached or supplier delayed) | High |
| `SLA_BREACH`: breached by 2 or fewer | Medium |
| `SUPPLIER_DELAY`: a pending request beyond its target | Medium |
| `SLA_APPROACHING` | Low |
| `RESERVE_CHANGE`: material change on a claim aged 30 days or less | Low |
| `SLA_UNKNOWN`, `SUPPLIER_UNVERIFIED`: evidence is missing | Low |

The spec's tiers do not place a supplier delay, a lone reserve flag or missing evidence; those placements are ours. High value alone is a flag, not a reason: an open claim nothing was triggered on has no severity. Closed claims have no SLA, supplier waits or severity.

## Overview and Stages & Aging (Stage A, item 4)

### DD-28 Shared filters narrow the engine's answer, in the API, and live in the shell state

Policy, broker, product and handler are query parameters of `claims.facts` (`ClaimFactsQuery`); the mock API narrows the claims before the engine runs, so `items` and `summary` always describe exactly the filtered claims and a screen never totals or recounts anything itself (CLM-FR-12). Broker and product reach a claim through its policy. The filters are one state for every claim screen (`filters.byScreen['claim-scope']`), so Overview, Stages & Aging and Claims always agree. The filters slice is now remembered in the browser (`ciq.filters`, written by every store, read once when the store is created, anything that is not a map of filter values ignored) and is cleared when the data set changes or the user signs out. The as-of date stays in the top bar. The filter choices come from the master data (policies by policy number, brokers, products) and from the users who handle claims. `ClaimsSummary` gains `open_unknown_stage`, the open claims among `unknown_stage`, so the stage table of open claims can say what is left over without counting closed claims.

Why: the owner's rule is that the UI never recomputes rules; a filter applied after the engine would make the cards and the list disagree.

### DD-29 What each card counts, and the click-through

Overview shows the snapshot at the as-of date: open and closed claims, paid to date (posted payments), outstanding reserve, incurred (paid plus reserve), SLA breaches (open claims past their stage target) and high-value open claims, all from the engine's summary. The spec's "new claims in period", "paid in period" and "average closed turnaround" cards need an event window the shell does not have; they are not built, and the summary already holds the turnaround for the later item that needs it. Each card, and each row of the stage and age tables, links to the Claims page with a criterion in the address (`/claims?show=open`, `closed`, `sla-breached`, `high-value`, `paid`, `reserve`, `incurred`, `stage:<Stage>`, `age:<bucket>`, with `unknown` for open claims with no stage or no reported date). A criterion only selects from the engine's facts for the current filters and as-of date; the money cards list the claims that have that figure above zero, so their amounts add up to the card. A test checks, over TEST and DEMO, three dates and five filter views, that every figure equals the claims its criterion selects, that each filter's values split the claims with none lost or counted twice, and that the stage and age rows add up to the open count (CLM-AT-03, -12). Overview's stage rows leave out Closed (closed claims are not open claims) and Reopened while no claim is in it.

The period cards this entry leaves out are built; see DD-33 for them and DD-36 for the one card whose list changed.

### DD-30 CSV: what is in the file

Overview, Stages & Aging and Claims each export what is on screen: the same filters, the same as-of date, the same order. Amounts are plain decimals with two places (`9000.00`) in columns whose header says BWP (`Paid (BWP)`); counts are plain numbers; a figure that does not apply (age of a closed claim, SLA of a closed claim) is an empty cell where the screen shows a dash. The Claims export is the whole filtered list, not the page on screen (paging is a viewing aid); the page count is "Showing 1–25 of 30". Overview's file has one row per card, stage and age bucket (`Section, Measure, Claims, Amount (BWP)`); Stages & Aging's has the stage and age rows with their money and an "All open claims" total (`Section, Item, Claims, Paid, Reserve, Incurred`). Files are named `claimsiq-<screen>-<data set>-<as-of date>.csv`, quoted per RFC 4180 with CRLF lines, and a text cell that starts like a spreadsheet formula (`=`, `+`, `-`, `@`) is prefixed with an apostrophe. The button gives no toast: the browser shows the download. One helper (`lib/csv.ts`) and one button (`claim-scope/ExportCsvButton`) serve every screen. The CLM-AT-14 check is a test per screen that parses the downloaded text and compares it to the cells on screen.

Overview's file later gained the period figures and a Days column (DD-35); the description of its columns above is the first version.

### DD-31 The 3 second check is a measured test on a generated 500-claim set

`src/read-model/test-support/generatedFixture.ts` builds a deterministic claims fixture of any size (the same count gives the same files; every claim reconciles with the engine, so it loads with no data issues) from the DEMO master data. It is a test aid, not a third data set of the product: the browser build bundles only TEST and DEMO. The check is a Vitest test (`features/overview/performance.test.tsx`) that renders Overview over a mock API holding 500 claims, with the API client's development-build response validation on, and fails if the cards, the age chart and the filter choices are not all there within 3 seconds; on the development machine it takes well under a second. A Playwright timing would measure a real browser but cannot load the generated set into the bundled fixtures without a third data set, so the browser flow runs on TEST and checks the figures, not the clock.

### DD-32 Claims list

The list shows id (a link to `/claims/<id>`, the claim detail page of a later item), client, product, current stage, age in days, handler, paid, reserve, incurred, SLA status and severity, sorted by any column (claim id by default; ties keep claim order) and 25 per page (25, 50 or 100). A banner names the criterion and the number of claims and offers "Show all claims"; an unknown criterion in the address is said so and every claim is listed. It has the loading, error (with Try again) and empty states, and a different empty message when a filter or criterion is what empties it. All personas see these three screens; nothing in the specs limits them.

### DD-33 Period figures: the window and the cohort logic (CL §5 CLM-01, §7; CLM-FR-02, -03, -06)

Replaces the sentence of DD-29 that left the period cards unbuilt. The period figures belong to the rules engine (`src/rules/period.ts`, `claimFacts.ts`, `summary.ts`), which `claims.facts` serves for a window named by the query parameter `period`; the screens compute nothing.

- **Window.** The shared filter bar offers Last 7 days, Last 30 days (the default), Last 90 days and Month to date. The window ends on the as-of date and includes it; "last N days" are the N calendar days ending that day (7 days ending 21 Oct start on 15 Oct); month to date starts on the 1st of the as-of month. Both ends are Africa/Gaborone calendar dates. The choice is stored with the other filters (`ciq.filters`) and survives Clear filters, which only clears the four narrowing filters. It shows on Overview, and on Claims while the page is listing a period criterion.
- **New claims in period:** claims whose reported date falls in the window. A claim with no reported date is in no window (it is not guessed) and shows in the age figures as unknown.
- **Paid in period:** the sum of POSTED payments whose payment date falls in the window. Approved, pending, void and rejected payments never count (CLM-AT-04, -11), so an approved-but-unpaid claim adds nothing. The card also says how many claims the payments were on.
- **Average closed turnaround (the cohort).** The cohort is the claims that are closed at the as-of date and whose closed date falls in the window. A claim that was reopened is open, so it is not in the cohort. The average is the mean of calendar days from reported date to closed date over the cohort claims that have both dates, to one decimal; a cohort claim with no reported date is left out of the mean and counted ("left out for missing dates"); a closed claim with no closed date at all cannot be placed in any window, so it is counted apart ("closed with no closing date") and shown on the card when there is one. With no averageable claim the card shows a dash, never zero. Both counts are in the CSV.
- **High-priority exceptions:** open claims with High severity at the as-of date (DD-27); not windowed.
- **Currently open** stays the snapshot at the as-of date (DD-29), beside paid to date, reserve, incurred, SLA breaches and high-value claims.

The facts carry the flags (`reported_in_period`, `closed_in_period`, `paid_in_period` per claim) and the summary counts them, so a card and the list behind it select from the same facts. Each period card opens the Claims page with a criterion: `new-in-period`, `paid-in-period`, `turnaround` (the turnaround card, listing exactly the claims it averaged; see DD-36) and `high-priority`. The spec says a card may open claims or claim payments; Stage A opens claims, and for the paid card the list adds a "Paid in period" column whose amounts add up to the card, so the payments behind it are visible. A claim payments screen is not built. The Overview groups its eleven cards under "As of {date}" and "{period}: {from} to {to}".

## Supplier Insights and Action Queue (Stage A, item 6)

### DD-40 Supplier Insights (CL §5 CLM-05, CLM-FR-08)

The supplier figures belong to the rules engine (`src/rules/suppliers.ts`, `summarizeSuppliers`), which the mock API serves as `suppliers.insights` over the same narrowed claims as `claims.facts` (the shared policy, broker, product and handler filters of DD-28); the screen computes nothing. One row per supplier of the data set, listed alphabetically and never ranked (no column sorts the table). A supplier's **cases** are the open claims assigned to it or holding a request to it (`isSupplierCase`, in `src/contracts`, so the engine and the Claims list's `supplier:<id>` criterion select the same claims). The figures:

- **Open requests:** requests to the supplier on open claims not completed at the as-of date; those with no request time are counted too and shown as "with no request time" (unverified, DD-26), and are not part of any wait.
- **Average and longest wait:** business days from the request to the as-of date (DD-23), over the open requests that have a request time. The average carries the number of requests behind it.
- **Past target (breaches):** open requests the engine marks `delayed` (waited more than `supplier_wait_target_business_days`, 5 in the demo config), so the screen and Claim Detail agree.
- **Open cases:** open claims assigned to the supplier (the claim's `supplier_id`).
- **Late actions:** tasks not done whose due date is before the as-of date (DD-42), on the supplier's cases. Only claim tasks count; a task is counted once per supplier whose case it is on.
- **Average turnaround:** business days from request to completion over the supplier's completed requests (on open claims; a closed claim has no supplier waits, DD-26), with the number of completed requests.

Clicking a supplier opens the Claims list with the criterion `supplier:<id>`: exactly its cases, as many as the figures were made from. The CSV (`claimsiq-suppliers-<data set>-<as-of>.csv`) has one row per supplier with every figure and its sample in its own column; an average held back is an empty cell. The export button is gated on the engine answer and the supplier names (`ExportCsvButton` now takes the list of queries the table is built from).

### DD-41 "Ranking not misleading on small sample": the minimum is 2 requests

An average is shown only from `supplier_min_sample` requests, a rule-config field of ours (the spec only says a small sample must not mislead), default **2**, with the sample size written beside every average ("14.0, 2 requests"; below the minimum: "1 of 2 needed"; none: "No requests" / "None completed"). The longest wait and the breaches are shown whatever the sample, because they are facts about named cases, not statistics. ### DD-42 Action Queue and the task rules (CL §5 CLM-06, CLM-FR-14)

### DD-45 Prototype mode: a build-time switch, and what an unset one means

A hosted demo has no Supabase (the hosting plan's two databases both belong to QuoteIQ), so a build can run in **prototype mode**: the sign-in is a role click, the data is the in-browser mock API, and nothing is needed at run time. The mode is chosen when the app is built, by `VITE_AUTH_MODE=prototype` (`bun run build:prototype`, `bun run dev:prototype`). It is not a runtime switch, so a deployed build cannot be talked into the other mode and the other mode's code is not in its bundle.

The default is the safe part. An explicit value wins and must be `prototype` or `supabase`. Unset, the dev server uses `supabase` (the local stack, as before). Unset, a production build uses `supabase` only when `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` are both set, and otherwise **the build fails** with a message naming both ways out. It never falls into a Supabase build that cannot sign anyone in, and never into a prototype build nobody asked for. `vercel.json` sets the mode in its build command, so Kwaku sets nothing in the Vercel dashboard. Prototype builds also drop the Supabase origin from the Content-Security-Policy: they may connect to their own origin only.

### DD-48 Stage B demo sign-in happens on the server

Owner's decision of 2026-11-07, matching QuoteIQ, built in Stage B: the demo roles stay on the sign-in page in every environment of the password build, and a click signs in **on the server**. The browser sends only the persona's e-mail to `POST /api/v1/auth/demo-sign-in`; the server accepts only e-mails on the demo account list, signs in to Supabase Auth with the demo password from its own environment (`DEMO_SEED_PASSWORD`, set per environment in Vercel and Doppler, never in the repository or the bundle) and returns the session (`access_token`, `refresh_token`, `expires_at`), which the client adopts with `supabase.auth.setSession`. This replaced the local quick-pick's password in code (DD-08); the no-password prototype session (DD-46) stays until the hosted demo moves onto the real backend, and the prototype build is unchanged.

The choices made in building it:

- **The list** is `src/contracts/demoAccounts.ts` (`DEMO_ACCOUNTS`, `isDemoAccountEmail`), the one list the sign-in page, the demo seed, `auth:personas` and the endpoint share; it holds no password. It left `src/ui` because the server needs it too.
- **A public endpoint.** The call comes before there is a session or a tenant, so it is in `publicEndpoints` of `src/contracts/endpoints.ts` (`public: true`, called by the SPA without a bearer token or tenant header) and mounted by `mountPublicEndpoints` ahead of the session and tenant middleware. A handler for it is required by type, as for every endpoint, and the route test checks that the API serves the public list too.
- **The password** is `DEMO_SEED_PASSWORD` in the config schema (optional, at least 6 characters, the minimum of Supabase Auth). `resolveDemoPassword` (`src/server/lib/config/demo-password.ts`) uses it; unset, the committed local `test1234` applies only when `APP_ENV` is `local`, and anywhere else there is no password. `auth:personas` uses the same resolution, so one variable gives the accounts and the sign-in the same password.
- **One refusal.** An e-mail off the list and a sign-in Supabase Auth refuses answer the same problem: 403, "Demo sign-in is not available for this account.", code `DEMO_SIGN_IN_REFUSED`; the reason is only in the server log (with the correlation id, never the password, the session or the e-mail). The endpoint therefore cannot be used to probe which accounts exist. A hosted environment without the password answers 503, "Demo sign-in is not configured in this environment.", code `DEMO_SIGN_IN_NOT_CONFIGURED`, for a listed e-mail only; an e-mail off the list is still the 403. Problem documents gained the optional `code` the SPA's client already read.
- **A sign-in client of its own.** The server signs in with a fresh anon-key client per call (`createSignInClient`), because supabase-js keeps the session of a sign-in in the client's memory even with persistence off, and the shared clients serve other requests.
- **The card.** In the password build the demo-accounts card is no longer development-only: `DemoSignInAccounts` is loaded lazily and not at all in a prototype build (the build-time comparison folds, so the prototype bundle holds no account e-mail, as DD-47 says). - **The bundle check.** `scan-bundle` fails any build that contains the committed local demo password, and a prototype build that contains a demo-account e-mail; `scripts/ci/scan-bundle.test.ts` tests both. A deployed password is never written into the repository or a rule; the server-variable-name rule already keeps `DEMO_SEED_PASSWORD` out of the bundle.
- **Not done here:** rate limiting the endpoint, and rotating the hosted accounts' password (a deployment step: set the variable and re-run the seed).

## Stage B database (Stage B, item 1)

### DD-49 The schema: plain SQL migrations, one table per entity, keyed (tenant_id, id)

The database is plain SQL under `supabase/migrations`, applied by the Supabase CLI (`bun run db:migrate`, `db:reset`), like QuoteIQ. Until `stage-b` was first pushed the migrations could be reshaped freely, because no shared or hosted database had them (the only one was a local stack that `db:reset` rebuilds, and CI starts on a fresh stack); from that push on, a pushed migration is never edited, a change is a new file, and its timestamp sorts after the last one. There is one table per entity of `src/contracts/entities.ts` (17), named as the plural of the entity and keeping the contracts' column names, so a row maps one to one onto its contract. Beside them: `task_audit_entries`, `task_counters`, `tenant_memberships` and `rule_configs` (DD-51).

- **Keys:** every table is keyed `(tenant_id, <entity>_id)` and every reference carries the tenant (`foreign key (tenant_id, policy_id) references policies (tenant_id, policy_id)`), so a claim cannot point at another tenant's policy: the database refuses it, whatever the API does. A reference that may be empty (a policy without a broker, a claim without a supplier) is a nullable column under the same composite key. A task's subject is one of four kinds of record and has no foreign key; its assignee does.
- **Money:** `numeric(18,2)` with `check (>= 0)`, BWP only (`check (currency = 'BWP')`). node-postgres returns `numeric` as a string, which is what DD-14 wants; the generated types say `string`.
- **Times:** the contracts' `Moment` (a date, or a time with the +02:00 offset, DD-14's sibling in `primitives.ts`) is stored as text in the `moment` domain, whose check is the same pattern, so a value reads back exactly as it was written and compares in time order (the offset is fixed). A time the source did not give is NULL and means UNKNOWN. `Instant` values the system makes (a task's `updated_at`, an audit entry's `at`) are `timestamptz`.
- **Enums** (statuses, priorities and so on) are text with a check, as in QuoteIQ, so a new value is one migration and no type to alter. The two lists that several columns share, the claim stages and the personas, are domains (`claim_stage`, `persona`) defined once. The seed test checks every enum column, and those domains, against the values the contracts name, so the SQL and the contracts cannot drift apart.
- **Tasks** (DD-20) carry the `Idempotency-Key` of their create in a column the contracts do not show, unique per tenant. The audit trail is append only for the application role (it may insert and read, never update or delete), and because removing a task would remove its entries, that role may not delete tasks either and the audit key does not cascade. Ids `TASK-0001` and up come from `next_task_id(tenant)`, a per-tenant counter.
- **Types:** `scripts/db/generate-types.ts` reads `information_schema` and writes the Kysely table types to `src/server/lib/db/generated/schema.ts` (`bun run db:types`). The migration test regenerates the file from a fresh database and fails when the committed copy differs, so a migration without the types cannot merge. QuoteIQ's route through the Supabase CLI's generator and an adapter was not copied: the CLI types `numeric` as `number`, and a second adapter existed only to undo that.

Why: the owner chose plain SQL migrations, generated types and `numeric(18,2)` on the plan card. The composite keys make the tenant a structural part of every row, which is the first of the two layers of DD-50.

### DD-50 Tenant isolation in two layers: the API's scope and row level security

The owner's decision, as in QuoteIQ: isolation is enforced in the API layer and, independently, by the database.

- **RLS.** Every table with a `tenant_id` has row level security enabled and one policy, `tenant_isolation`, for the role `claimsiq_app` only: `tenant_id = app_tenant_id()` for reading and writing, where `app_tenant_id()` reads the transaction-local setting `app.tenant_id`. Without the setting the policy compares against NULL, so a session with no tenant sees nothing and writes nothing. `enable_tenant_isolation(table, mode)` does this and the grants for each table (the mode is named: `full`, `no_delete`, `append_only` or `read_only`), called once right after the table is created, so no table is isolated by remembering to; the migration test fails on a table without RLS and the policy. `anon` and `authenticated` hold no privileges on any table (default privileges are revoked for them), so Supabase's REST API shows nothing.
- **Two ways in.** The owner (`postgres`) bypasses RLS and is used for the migrations, the seed and the membership lookup (the tenant is not known yet). The API runs every tenant request in `withTenant` (`src/server/lib/db/tenant.ts`): one transaction, `set local role claimsiq_app`, `set_config('app.tenant_id', <tenant>, true)`; both last for the transaction only, which is what a transaction pooler allows.
- **The API's scope.** `withTenant` hands out a `TenantScope` whose `selectFrom`, `updateTable` and `deleteFrom` already carry `tenant_id = <tenant>` and whose `insertInto` writes the tenant itself and does not accept one in the row. The tenant id is a branded `TenantId`. A forgotten predicate is caught by RLS and a forgotten role switch by the predicate.
- **Who may enter which tenant.** `tenant_memberships` links a Supabase Auth user to a tenant and the persona the account starts in (the four demo personas, DD-08; the persona remains a view, DD-07). `resolveTenantAccess(db, authUserId, 'TEST')` is the only way to a `TenantId`: the `X-Tenant-Id` header is a request, not a credential. An unknown tenant, a malformed one and a tenant the user is not a member of give the same answer, so a caller cannot probe which tenants exist. The membership table references `auth.users` with `on delete cascade`.
- **Not done here:** the Hono middleware that calls these (DD-48's sign-in and the API are separate items), and any cross-tenant administrator.

### DD-51 Rule configuration per tenant and data set

`rule_configs` holds one row per tenant and data set: the validated rule configuration as `jsonb` (the shape of `src/contracts/ruleConfig.ts`), a `version` that counts saves, and who saved last. It is seeded from `fixtures/v2/proposed_rule_config.json` for TEST and DEMO, so the engine sees the same thresholds in both transports. The data set is part of the key and a composite foreign key ties it to the tenant's `dataset_tag`, so a tenant cannot hold a configuration for the other data set. The configurable rule editor (DD-61) edits this row and records each change in `rule_config_audit_entries`.

### DD-52 Scripts and the seed

- `db:migrate` is `supabase migration up --local`. `db:reset` rebuilds the local database from empty: `supabase db reset` (all migrations), then `auth:personas` (the reset recreates Auth's tables, accounts included), then the seed. It refuses anything but the local stack: `APP_ENV=local` and a `DATABASE_URL` on 127.0.0.1 or localhost. `db:seed` and `db:types` complete the four scripts; `supabase:start`, `supabase:stop` and `auth:personas` are unchanged. `DATABASE_URL` is a new optional variable of the config (`.env.local.example`, `.env.example`, `run.ps1` and CI write it from `supabase status`). The SQL seed of the CLI is switched off: the data goes through the loader.
- **The seed goes through the fixture loader** (`src/read-model/fixtures`, DD-15 to DD-17), so a row is accepted or quarantined by exactly the rules the mock API applies, and TEST and DEMO load as the tenants `TEST` and `DEMO`. A quarantined row is reported (file, line, record, field, problem, fix) and never inserted; a row with missing evidence loads with NULL and counts as a warning. The seed validates the rule configuration with `RuleConfig` before it stores it.
- **A seed replaces the data set**: in one transaction it deletes the tenant's rows (tasks and audit trail included, the same as Reset) and inserts the loaded ones, so a second run changes nothing and a failed run leaves the old data. Rows go in with `jsonb_populate_recordset` in batches of 500, with the column list taken from the contract's schema.
- **Memberships:** every demo account found in local Supabase Auth gets a membership in both tenants; the persona is its e-mail's local part (`head.of.claims@` is `head-of-claims`). Without the accounts the seed says so and links nobody.
- **Local only for now:** the seed refuses a database that is not the local stack, because it replaces a tenant's tasks. A hosted database is a later decision.

### DD-53 Database tests use scratch databases

The database tests (`scripts/db/seed.test.ts`, `scripts/db/isolation.test.ts`) create a throwaway database on the local Postgres, apply the migrations to it (with a stand-in `auth.users` table, the one outside thing the schema points at), seed it and drop it, so they never touch the data of the stack and run in parallel with every other test. They skip themselves when the stack is not up or `DATABASE_URL` is unset, as the token tests do; CI starts the stack, rebuilds the database with `db:reset`, and runs the unit project through `ci:test:unit`, which fails on a skip. The checks: every table has RLS and the tenant policy, `anon` and `authenticated` read nothing and the committed types equal the schema; the seed's counts equal the fixtures and the TEST figures equal `expected_metrics.json` (6 claims, 9,000.00 paid, 68,000.00 reserve); a bad row is quarantined and not inserted; a second seed gives the same state; a TEST session sees no DEMO row in any table, cannot write one, a session with no tenant sees nothing, and a claim cannot point at another tenant's policy (DEMO is given a task and an audit entry for this, since the fixtures have none); the application role can delete neither a task nor an audit entry; every enum column allows exactly the values of the contracts; and Supabase's REST API answers the anonymous key 401, permission denied.

## Stage B API (Stage B, item 2)

### DD-54 One Hono app for `/api/v1`, one route per contract endpoint

The API is a Hono app (`src/server/lib/router/app.ts`) written as one Vercel function (`api/v1/index.ts`, not deployed yet: DD-59) and served locally by `scripts/dev/serve-api.ts` over `node:http`. Routes are mounted from the contract list (`src/server/lib/router/contract.ts`): a handler table typed `{ [K in keyof Endpoints]: Handler }`, so an endpoint without a handler does not compile, and a test (`src/server/tests/unit/api/contract-routes.test.ts`) fails when the app serves anything but the contract list and the health check. For every request the mount validates the query (400) and the body (422) with the contract's own zod schemas, runs the handler, and checks the answer against the contract's response schema: a drifting handler is a 500 with the cause in the log, never a wrong answer on a screen.

Middleware, outermost first: security headers, correlation id (`X-Correlation-Id`, echoed in the response and in every problem document), session, tenant, routes. Errors are `application/problem+json` in the shape the SPA's client normalizes (`type`, `title`, `status`, `errors[]` of `{field, code, message}`, `correlationId`). An unexpected error answers 500 with no detail and logs only the message and the id.

- **Session (401).** `Authorization: Bearer <Supabase access token>` verified by `src/server/lib/auth/verify.ts` (JWKS, ES256/RS256 only, pinned issuer, role `authenticated`). Missing or invalid: 401 with `WWW-Authenticate: Bearer`; the reason goes to the log, never to the client. JWKS unreachable: 503.
- **Tenant (400/403).** `X-Tenant-Id` is a request, not a credential: on every request `resolveTenantAccess` checks it against the user's memberships (DD-50). Missing header: 400. A tenant that does not exist and one the user does not belong to: the same 403.
- **Context.** `X-As-Of` (default 2026-10-21, 400 when not a date) and `X-Persona`, the actor of commands (400 on a command without one). Nothing in a handler touches the database except through `ctx.tenant` (`withTenant`) or, for the reset, the owner connection.

### DD-55 One read model for the mock API and the server (`src/read-model`)

The two transports must give the same answers, so they share one layer, pure like `src/rules` (lint-enforced): `fixtures/` (the CSV loader, moved from the mock API), `asOfViews.ts` (claims and invoices as an as-of date sees them), `reads.ts` (the answer of every read endpoint as a function of a `ReadModel`: the records, the tasks with their audit trail, the rule configuration, the data issues), `taskRules.ts` (what creating, assigning and changing the status of a task do, audit entry included, and which changes are refused) and `problems.ts` (the field-level problems and `InvalidValues`, the one refusal both transports turn into a 422). Only the source differs: the mock API builds the `ReadModel` from the parsed fixtures and the changes kept in the browser, the server from the tenant's rows (`src/server/lib/read-model/load.ts`, one transaction, every row parsed with its contract). `claims.facts`, `claims.paidTrend`, `claims.whatIf`, `suppliers.insights` and the `overdue` flag therefore run the same `src/rules` functions over the same record shapes on both sides. `scripts/db/api-parity.test.ts` asks the server and the mock API every read endpoint and requires identical answers. The loader, the as-of views and the generated-fixture test aid now live in `src/read-model` (`fixtures/`, `asOfViews.ts`, `test-support/`), and the entries above that name them (DD-15 to DD-17, DD-31, DD-52) carry the new paths; Hono, declared by DD-02, is used from here.

Two details that keep the answers equal: the database keeps the order the fixture gave (`row_no`, an identity column on the master and transaction tables, because a select without an order is not ordered), and `tasks.list` returns tasks in id order on both sides (the mock API used to move an edited task to the end). The loader's `quarantinedRows` field is gone: the count of rejected rows is derived from the issues (`quarantinedRowCount`), the one definition both transports use. `data_issues` holds what the loader rejected or flagged when a data set was seeded, so `data.issues` is served from the database too.

### DD-56 Tasks and their audit trail in the database

Create, assign and change status are one `withTenant` transaction each: the shared task rules compute the new `TaskRecord`, the server writes the changed row and the new audit entry together, so a task and its trail cannot disagree. Ids come from `next_task_id(tenant)`. A create with an `Idempotency-Key` takes a transaction-level advisory lock on the key, looks the key up and returns the earlier task, so two simultaneous retries make one task. The audit entry's `actor` is the persona acting (`X-Persona`, as in DD-20); the signed-in account is recorded beside it in `task_audit_entries.actor_user_id` and is not shown on a screen. A task created with an assignee logs two entries, CREATED and ASSIGNED (from nobody to that person), the same instant and actor, so the trail shows who was given the task as it does for every later assignment; both transports do this in `createdTask`. A status change the contracts' transitions do not allow is a 422 on the field `status`; an unknown task is a 404; a subject (as of the date) or an assignee that does not exist is a 422 on its field. The dialogs that choose an owner or a claim show their list as "Loading…" in a disabled select until it arrives (`Select`'s `loading`), so Assign is never offered over an empty list.

### DD-57 Reset in API mode: restore the tenant's data set, local and dev only

`POST /api/v1/demo/reset` replaces the active tenant's data set with the committed fixture, by the same code as the seed (`src/server/lib/seed/replace.ts`): rows, data issues, rule configuration, tasks and their audit trail, and the task counter. The tenant's memberships are kept (removing a tenant row removes them, so they are saved and put back). It runs as the owner, because the application role may delete neither tasks nor their audit trail, and only after the tenant middleware has proved the caller a member. It is allowed only when `APP_ENV` is `local` or `dev`; anywhere else it answers 403 and changes nothing. Why: the reset rewrites a tenant's data, which no hosted environment should let a click do, while the local stack and a development environment are exactly where the demo's "Reset" has to work. The other tenant is untouched. The seed script keeps its stricter rule (local stack only, DD-52). Reset means "back to the fixture", so it restores the rule configuration too; the configurable rule editor (DD-61) follows that rule: a saved rule edit and its audit do not survive Reset.

### DD-58 The SPA picks the transport at build time; how the dev setup runs

A prototype build keeps the in-browser mock API (DD-45, DD-46). Every other build sends its calls to `/api/v1` with the platform `fetch`: the API client already adds the session's bearer token, `X-Tenant-Id`, `X-As-Of`, `X-Persona` and the `Idempotency-Key` per request, and signs the user out on a 401. `main.tsx` imports the mock transport behind an inline `VITE_AUTH_MODE === 'prototype'` comparison, so a Supabase-mode bundle carries neither the mock API nor the fixtures. In development Vite proxies `/api` to the API server (`API_PORT`, default 5274), so the SPA uses its own origin as it will on Vercel and the Content-Security-Policy needs no new origin.

`bun run dev` starts the API server and the SPA together (`scripts/dev/dev-all.ts`; Ctrl+C or either one stopping stops both); `dev:api` and `dev:ui` start one each, and `dev:prototype` is unchanged (SPA only, no stack). The stack project of the Playwright suite starts its own API (port 5382, `E2E_API_PORT`) and Vite (5380) and signs in through real Auth; its specs change TEST and DEMO data and end with Reset.

### DD-59 The API ships to Vercel only once a hosted database exists

The hosted demo stays the static prototype build (DD-45): no function and no database environment. Vercel treats every file under `api/` as a function, so `.vercelignore` leaves `api/` out of the deploy, and `vercel.json` carries no `/api/v1` rewrite and no `functions` entry. `api/v1/index.ts` stays in the repository, built and tested through the same Hono app as `bun run dev:api`, for the day a hosted database exists.

To ship the API then, three lines change: (1) add `{ "source": "/api/v1/:path*", "destination": "/api/v1" },` as the first entry of `rewrites` in `vercel.json` (before the SPA fallback); (2) add `"functions": { "api/v1/index.ts": { "maxDuration": 30, "includeFiles": "fixtures/v2/**" } }` to `vercel.json` (`includeFiles` is what lets Reset read the fixtures); (3) delete the `api/` line from `.vercelignore`. The environment (`DATABASE_URL`, `SUPABASE_*`, `APP_ENV`) is then set in Vercel, and DD-57 decides whether Reset is available there.

## Stage B P1 features (Stage B, item 3)

### DD-60 Claim stage what-if (CLM-FR-19)

The what-if is a read, `claims.whatIf` (`GET /api/v1/claims/:claimId/what-if?to_stage=<stage>`), answered by `reads.claimsWhatIf` in `src/read-model`, so the mock API (prototype build) and the Hono server give the same answer (`scripts/db/api-parity.test.ts` asks both for every claim and every stage, legal or not). Nothing is written, audited or kept: the SPA holds the chosen stage in component state only, so leaving the page, a change of data set or as-of date, or Reset restores the real view.

The answer holds `current` (the claim's facts as `claims.facts` gives them), `next_stages` (the stages the claim may move to) and `what_if` (`to_stage`, `event_at`, `facts`), which is null when no `to_stage` is asked for. Without `to_stage` the read only names the choices, which keeps the legal-move table on the server side of the contract: the SPA does not copy it.

The what-if is `withHypotheticalStage` in `src/rules/transitions.ts`: one `ClaimEvent` stamped at the end of the as-of day (`23:59:59+02:00`), so it sorts after any real event of that day whatever its time (`~what-if` as its id settles a tie with a real event stamped the same second), appended to the claim's events as the as-of date sees them; the engine then runs unchanged (`computeClaimFacts`). The record fields that event would change move with it (recorded stage, status OPEN or CLOSED, closed date set on closing and kept on reopening), so the stage check does not report a discrepancy that is only the preview. The SLA anchor therefore moves only by the engine's own logic (CL §7, DD-23 to DD-26): the stage clock starts on the as-of date, so the claim has 0 business days in the new stage; a Closed claim has no clock and no severity; Reopened has no target, so its SLA is unknown (DD-26), never within; an undated event on the claim still makes the SLA unknown.

Legal moves (CL §8 gives only "possible next step" prose): a closed claim may only be reopened; a Reopened claim returns to an active stage (Triage to Settlement) or closes again; any other claim may move to any stage except the one it is in, New and Reopened, forwards or back, because the fixtures themselves skip stages (New to Closed, New to Approved). The current stage is the engine's (`current_stage`, or the recorded stage when the claim has no dated event). A stage that is a valid stage but not a legal move is refused as a 422 field problem on `to_stage` through `InvalidValues`; a value outside the stage list fails the query schema (400, as every other query does); an unknown claim is a 404.

Claim Detail shows it in a card, "Stage what-if", labelled "What-if: not saved", with a stage select (only the legal moves), a Reset button and a table of the real and the what-if stage, stage SLA (chip and sentence from the same texts as the flag card), severity and the date the stage clock starts (the date only, as the clock counts days). It has loading, error and empty states, and the restricted state a 403 gives; no persona is restricted from it, as the spec limits nothing by persona (DD-43).

### DD-61 Configurable rule editor (CL §2 P1 "configurable rule editor"; Reset is CLM-FR-18)

A Rules page (`/rules`, seventh destination, `features/rules`) edits the rule config of the active tenant and data set. The spec says only "configurable rule editor" (CL §2) and that the demo thresholds are configurable (CL §8, §9); everything below is our build decision. Reset must bring the flags back to the expected state (CLM-FR-18), which is why a saved rule does not survive it.

- **What is editable:** every value of `ClaimsRuleConfig` except the working week and the holiday switch: the six stage SLA targets, the supplier wait target and sample minimum, the material reserve change (amount and percent), the high-value line, the approaching window, the two severity cut-offs and the age bucket limits. `business_days` and `holidays_excluded` stay as the spec fixes them (Monday to Friday, no public holidays: a documented Sprint 01 simplification, CL §8), so a page that cannot honour a different calendar does not offer one. `as_of` of the config is kept.
- **Validation is the existing schema.** It moved from `src/rules/config.ts` to `src/contracts/ruleConfig.ts` (the endpoints need its shape and `src/contracts` cannot import `src/rules`); `src/rules/config.ts` re-exports it and keeps `parseRuleConfig`. `EditableClaimsRules` is the same values with no defaults, so a save names every one and an omitted value cannot silently reset. The page checks a draft with that schema before it enables Save, and the API checks it again (422, field `claims.<value>`). The values are text fields that keep exactly what is typed (a number field would quietly drop `-5` or `abc`), checked on every keystroke; `features/rules/draft.ts` turns every schema problem into a plain `t()` message in one place (not a number, not a whole number, at least N, at most N, limits must increase), so no schema wording reaches the page. The Reset dialog names the saved rules and their history.
- **Endpoints** (`src/contracts/endpoints.ts`): `rules.config` (`GET /api/v1/rule-config`: `config`, `defaults` = the spec's `proposed_rule_config.json`, `version`, `saved_at`/`saved_by` (null until a first save), `audit`), `rules.save` (`POST /api/v1/rule-config`, body `{ version, claims }`) and `rules.restore` (`POST /api/v1/rule-config/restore`, body `{ version }`); both writes answer with the new state. They answer through `src/read-model` (`reads.ruleConfig`, `ruleConfigEdits.ts`) in both transports, and `scripts/db/api-parity.test.ts` asks both through saves, refusals and a restore. `ReadModel` carries the config in force and its history; every read that runs the engine therefore runs on the saved config, which is what makes a save apply to every screen and CSV export at once (the SPA invalidates every query after a save).
- **Audit:** one entry per changed value, not per save: `version`, `at`, `actor` (the persona, as for tasks), `action` (`CHANGED` or `RESTORED`), `field` (`high_value_incurred_BWP`, `stage_sla_business_days.Assessment`, `age_bucket_upper_days`), `from` and `to` as text (`25000`, `7, 30, 60, 90`; null where a stage target is added or removed). The entries of a save share its `version`. A save that changes nothing makes no version and no entry. The page shows them newest first. The order of the values is the schema's, never the object's key order, because Postgres `jsonb` rearranges keys (the parity test found it).
- **Who may:** Head of Claims and Finance (`RULE_EDITOR_PERSONAS`). Another persona gets the page read-only (a banner saying why, the saved and default values in a table, the history). The server refuses a write by any other persona with 403 and one that names no persona with 400. The persona is the `X-Persona` header, as for every command (DD-07): it is recorded and checked, but it is not authentication, so this stops what the UI does not offer and cannot stop a caller who sends another persona's header. Authentication stays the Supabase session and the tenant membership.
- **Concurrency:** `version` counts the saves (1 as seeded). A write names the version it started from; any other is a 409 and changes nothing. The server locks the tenant's `rule_configs` row (`for update`) so two saves of one tenant meet in turn. The page, on a 409, shows the latest rules and a banner "saved by someone else first" and drops the draft: the editor is keyed on the version.
- **Storage:** the prototype build keeps the saved claims block, version, time, persona and audit in the same browser-storage record as the tasks (`changes.ts`, key per data set and tenant), so a reload keeps them and Reset removes them. API mode updates the tenant's `rule_configs` row (`config`, `version`, `updated_at`, `updated_by`) and appends to a new table `rule_config_audit_entries` (migration `20261107000800_rule_config_audit.sql`: tenant-keyed, `enable_tenant_isolation(…, 'append_only')`, `actor_user_id` beside the persona, written inside `withTenant`). Both are per tenant and data set; TEST and DEMO never share a config.
- **Restore defaults** puts the spec's config back as an audited change (`RESTORED`, one entry per value that differed) and is confirmed in a dialog, like Save (who, scope, result; Save lists each old and new value). **Reset** (DD-57) restores the config and clears the audit, as it clears tasks and their trail: `replaceDataSetRows` deletes `rule_config_audit_entries` before `rule_configs` and re-seeds version 1.
- **Seen working (TEST):** at P25,000 CLM-106 (P30,000.00 incurred) is the one high-value claim; saved at P40,000 the Overview card reads 0 and the Exceptions CSV has no high-value reason; Restore defaults brings the one claim back.

### DD-62 Paid by month and supplier wait percentiles (CL §2 P1 "claims paid trends", "supplier scorecard percentile chart"; CLM-FR-20)

CLM-FR-20 says only "show supplier trend with baseline" and "rankings use denominators and sample-size context"; the period and the percentile method are our build decisions.

- **Paid by month (Overview).** A new read, `claims.paidTrend` (`GET /api/v1/paid-trend`, the four claim filters, answered by `reads.claimsPaidTrend` in `src/read-model` in both transports and in `scripts/db/api-parity.test.ts`), computed by `paidTrend` in `src/rules/trend.ts`. The granularity is the **calendar month**, because the spec names none and the period selector (7, 30, 90 days, month to date) is a card window, not a bucket size. A payment is in the month of its Africa/Gaborone paid date; only POSTED payments dated on or before the as-of date count (the same `postedPayments` that makes paid to date, so approved, pending, void, rejected and later-dated payments are in no bucket). Buckets run from the month of the first posted payment to the as-of month with no month skipped (a month with no payment is `0.00`, not a gap); the as-of month ends at the as-of date. Each bucket carries its amount, payment count and distinct claims; the sum of the amounts is `total`, a decimal-string sum, equal to the claims' paid to date. The period selector does not narrow the chart (its subtitle says so); the four filters and the as-of date do. The chart is a bar chart of the posted paid per month; the Overview CSV gains a "Paid by month" section, a row per month (claims, amount) and a "Posted paid to date" row.
- **Percentile method: nearest rank** (`nearestRank`, `src/rules/percentile.ts`). Of n waits in order, the p-th percentile is the value at rank ceil(p/100 × n) counted from 1, computed in integers. It always returns an observed wait (business days are whole numbers), needs no interpolation, and is easy to check by hand: the median of two waits is the lower one, the 90th percentile of fewer than ten waits is the longest.
- **Which waits.** The open requests with a request time, in business days from the request to the as-of date: exactly the sample behind "Average wait", so one sample size explains both. Completed requests stay in "Average turnaround".
- **Baseline.** Two: the supplier wait target (`supplier_wait_target_business_days`, a reference line on the chart; each percentile is `within` it when at or under, `over` when above, the same edge as the engine's `delayed`), and the percentiles of every supplier's open waits taken together (`all_suppliers`, shown as the first row and bar group). Both come from the saved rule config, so an edit in the rule editor changes the result.
- **Small samples.** A supplier with fewer than `supplier_min_sample` open waits (and the pooled baseline likewise) has its sample size shown and `median`, `p90` and both placements `null`: the screen says "Not enough data: 1 of 2 needed" and the chart leaves it out. When no supplier is placed the chart is replaced by a "not enough data" note. Nothing is sorted or ranked: suppliers stay alphabetical, and the words are "within" and "over the target", never best, worst or rank. With both fixtures' two requests with one supplier and a minimum of 2, TEST shows median 11 and 90th percentile 13 business days, over the 5-day target; at a minimum of 3 neither is shown.
- **Supplier Insights** shows the chart and a table (requests behind it, median, 90th percentile, each with its placement) in a card under the supplier table; its CSV gains the median, 90th percentile and their placements after the wait sample, and a last row for the baseline.
- **Shared SPA files this item changed:** `components/charts` gained `GroupedBarChart` (side-by-side bars, an optional dashed reference line, the same accessible data table as the other charts); the rules page's hint for the sample minimum now says percentiles too; `router.test.tsx` waits for the supplier card title, since a supplier name now appears in two tables.
- **Wording.** Every count in the two cards has a singular and a plural form (`_one` / `_other`, the `count` parameter of `t()`): "1 payment over 1 month", "from 1 request". No text speaks of ranking suppliers, even to deny it. The Paid by month subtitle takes its as-of date from the app's data context, not from the answer, so it never reads "up to —" while the answer loads.
- **Seen working (TEST):** Overview's Paid by month reads Sep 2026 P5,000.00 and Oct 2026 P4,000.00 (P9,000.00 over 2 payments), the same as Paid to date; at 10 Oct, Oct 2026 is P0.00. Supplier Insights shows Mma-Motor Repairs with 2 requests, median 11 and 90th percentile 13 (both over the target); saving a sample minimum of 3 in the rule editor turns both into "Not enough data: 2 of 3 needed".

### DD-63 Executive one-page digest (CL §3 P1 "executive one-page digest"; SF §3 "one credible print/PDF-like executive summary")

The specs name the digest and nothing more: CL §3 lists it as P1, SF §3 asks for "one credible print/PDF-like executive summary", and CL §4 gives the questions of Finance / COO / MD ("Where have reserves shifted and what has actually been paid? Is claims service performance deteriorating?"). Everything below is our build decision.

- **A page, no new number.** `/digest` (`features/digest`, nav after Action Queue) calls the typed endpoints the screens call (`claims.facts`, `suppliers.insights`, `suppliers.list`, `tasks.list`, `users.list`) and adds no endpoint, no read and no calculation. Its five sections are made from the rows the screens build: the headline figures are `overviewFigures` (the Overview's 11 cards, hints included); the top exceptions are `exceptionRows` in the Exceptions screen's default order, with its sentence ("4 claims need review: 3 High, …"); the material reserve movements are the `material` entries of `reserve_movements` of the open claims, newest first, with the test that made each material (`materialBasis`, as Claim Detail shows) and the engine's count of open claims with one beside them; the supplier delays are the suppliers of `supplierRows` with an open request past the target or one with no request time, with the median and 90th percentile and their placement from DD-62 and the all-supplier baseline as a sentence; the open actions are `queueRows` without the done tasks, in the Action Queue's own order. `scope.facts` is the page's one gate: its loading, empty ("No claims to summarize") and error states are the page's; each other section has its own loading, error with retry and empty state, so one failed read does not blank the sheet. - **Filters and the as-of date.** The page shows the shared filter bar (with the period) and takes the as-of date and data set from the shell. ### DD-64 Sidebar: the whole profile menu and a width toggle in the icon strip (pilot feedback)

A pilot tester's screenshot showed the profile menu cut off at the edge of the 72px icon strip ("Signed i…", "Sig…"), and the only way to read a screen's name was to hover over its icon.

- **The menu.** `.ciq-sidebar` clipped sideways (`overflow-x: hidden`), so the 240px menu of the user card was cut at 72px. Between 768 and 1279px the sidebar now has `overflow: visible`; the scrolling for a short window moved to the navigation list (`.ciq-nav`, `overflow-y: auto`), so the brand, the user card and the toggle stay in view. The menu opens fully over the page, above the top bar (z-index 60 in the sidebar's layer of 40), in both themes. At 1280px and above, and in the drawer below 768px, the CSS is as it was.
- **The toggle.** A button at the bottom of the sidebar, labelled "Full sidebar" (icon only in the strip, with the label as its tooltip and accessible name; icon and label in the full sidebar). The name stays the same and `aria-expanded` carries the state, so a screen reader says "Full sidebar, button, expanded" and not a changing verb. The global focus ring shows on keyboard focus. It is rendered only between 768 and 1279px (`RAIL_QUERY` in `useMediaQuery.ts`, the same range as the rail's CSS), so nothing exists to focus at 1280px and above or in the drawer.
- **Expanded means the full sidebar** (tenant, wordmark, "Claims Intelligence", the screen names, the user name and persona), the width of the sidebar at 1280px and above. It **pushes** the content (the grid column becomes `--ciq-sidebar-width`) instead of floating over it, because an overlay would hide the left edge of the page, including the page title in the top bar, with no way to scroll to it. The cost is room: at 768px the content is 524px wide, so below 1200px the top bar puts its data controls on a second row, as it does in the drawer layout. The full sidebar gets a hairline on its right edge, so it reads against the page in the dark theme.
- **Remembered per browser** under `localStorage` `ciq.sidebar` (`readStoredSidebarExpanded` / `storeSidebarExpanded` in `lib/storage.ts`, guarded like `ciq.theme`). Only the value "expanded" expands; no value, "collapsed" or anything else is collapsed. The choice is kept while the window is outside the range and applies again on return; it is a view preference, not part of the session.
- **Not built:** the toggle at 1280px and above (the full sidebar is the only layout there), a hover-to-expand strip, and closing the full sidebar by clicking the page.
- **Seen working** (prototype build, Chromium, light and dark): at 800 and 1100px the profile menu opens in full beside the strip, and in the full sidebar; the toggle expands and collapses the sidebar and the state survives a reload; at 1400px there is no toggle and the sidebar is unchanged.

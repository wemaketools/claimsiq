# Acceptance: CLM-AT-01 to CLM-AT-16

The acceptance scenarios of the requirements (CL §11), where each is asserted and the result. They run against the specs' synthetic fixtures (the TEST data set) with the as-of date 21 Oct 2026, in both modes of the app: the **prototype** project (the hosted-demo build on the in-browser mock API) and the **stack** project (the SPA over the Hono API and the local Supabase database).

**How to run them:** `bun run test:e2e` runs both projects (the stack project needs the local Supabase stack and the built database, `bun run supabase:start` and `bun run db:reset`; Playwright starts its own API and Vite). `bun run test:e2e:prototype` runs the prototype project alone: it builds the hosted-demo build and needs no Supabase stack. One spec, `e2e_tests/specs/acceptance.spec.ts`, runs in both; every assertion block is a `test.step` named after its scenario, so a failing step names the scenario it breaks and the Playwright project it failed in.

**Where the modes differ.** Only in how the four test-only scenarios (AT-09, 10, 11 and 16) get their extra rows (note 1): the prototype rewrites the bundled CSV on its way into the browser, the stack inserts the same rows into the local database and deletes them after the test. Sign-in (a role click), Reset, the screens and every assertion are the same, except that the prototype has no Data set switch (it serves DEMO), so its run puts TEST in view through the `ciq.prototype.dataSet` storage key (`selectDataSet` in `specs/support.ts`) and the stack run uses the select. In the stack the Reset at the start of each flow restores the TEST tenant in the database, and the project runs on one worker because its specs share that database.

## Notes and spec gaps

1. **Test-only rows (CLM-AT-09, 10, 11 and 16).** The specs' TEST and DEMO data has no claim with a missing event time, an event written out of order, a pending or rejected claim payment, or a reopened event, so a browser run cannot show these on the shipped data. The acceptance spec adds a few rows (`e2e_tests/specs/testOnlyRows.ts` holds them once). In the prototype project it rewrites the page's script response on its way in, appending the rows after a named fixture row, and fails the test if a row's anchor is not found; in the stack project it inserts the same rows into the local database's TEST tenant as the owner (refusing a database that is not local), reloads the page, and deletes them after the test (a Reset would too). `fixtures/v2` is never edited and nothing in the product knows about the rows. They are: a `Reopened` event for CLM-103 (18 Oct 2026), an event for CLM-105 with no time, an earlier event for CLM-106 written after the later ones, a PENDING payment of P3,000.00 on CLM-104 and a REJECTED payment of P2,000.00 on CLM-106. The scenario text for CLM-AT-16 allows this ("if a reopened-event fixture is supplied"); there is no Reopen button in the P0 screens, because the history comes from the events the data carries.
2. **CLM-AT-15 and Premium Collections.** There is no Collections screen in this repository yet (the link question is open in the Collections issue). The scenario is met by the in-app policy invoices view (`/policies/:policyId/invoices`, DD-39), which takes `policy_id` and keeps exactly the invoices that carry it, with no name matching, and is marked on screen as a stand-in. The step navigates to it from the claim. When Collections exists, the link changes target and the join stays on the identifier.
3. **CLM-AT-12 and the handler filter.** Every claim in both data sets has the same handler (USR-CLM, Boitumelo Demo), so the Handler filter can only select all of the claims; the acceptance step shows that it agrees on every screen but cannot show it splitting a book. Broker and product do split it, and the filter tests check that every filter's values partition the claims without loss over the data they have.
4. **CLM-AT-07 wording.** The scenario says P30,000 "exceeds" the P25,000 line; the rule in CL §7 and the config is "gross incurred at or above P25,000" (DD-27 builds it that way). CLM-106 meets both readings.
5. **Not covered by the browser run.** The 3 second budget on 500 claims (CL's performance requirement) is a measured SPA test on a generated claim set, `features/overview/performance.test.tsx` (DD-31), because the browser build bundles only TEST and DEMO.

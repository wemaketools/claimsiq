# Testing and CI

Status: as built (scaffold, data layer, rules engine, the Stage B database, claim screens, exceptions, claim detail, policy invoices, supplier insights, the action queue, prototype mode and the acceptance pass). The decisions behind it (CI and checks, Bun) are in `docs/plan/design-decisions.md`.

## Test projects

| Project | Where | Runner and environment | Command |
|---|---|---|---|
| Root `unit` | `src/server/tests/unit`, `src/contracts/**`, `src/mock-api/**`, `src/rules/**`, `scripts/**/*.test.ts` | Vitest, node environment, 20 s timeout | `bun run test:unit` |
| Root `integration` | `src/server/tests/integration` (does not exist yet; `passWithNoTests` is on until it does) | Vitest, serial, 180 s timeouts | `vitest run --project integration` |
| SPA | colocated `src/ui/src/**/*.test.ts(x)` | Vitest, jsdom, React Testing Library, jest-dom; setup `src/ui/src/test/setup.ts` | `bun run test:ui` |
| E2E | `e2e_tests/specs` | Playwright + `@axe-core/playwright`, Chromium, 1440×900 | `bun run test:e2e` |

`bun run test` runs both root projects. Vitest is the runner everywhere; `bun test` is not used. Root tests see the values of the git-ignored `.env.local` (`vitest.config.ts` parses it), so they behave like the scripts.

Conventions: fewer, broader tests. A test sets up once and walks a realistic flow with several assertions (sign in, walk the pages, switch persona and theme, reload) instead of many tests that each check one or two things; a test names the behavior it protects, and assertions that only pin a constant or a class name are left out. Tests are deterministic and order-independent. Helpers for the SPA are in `src/ui/src/test`:

- `renderWithProviders(element, options)`: the element in the store, a stub auth context, toasts and a memory data router, with the API client adapters wired to the store.
- `renderRouteTree(routes, options)`: the same providers around a whole route tree, for example the application's own (`buildRoutes`); `renderWithProviders` is built on it.
- `restoreAfterEach(restore)`: registers the restore function returned by `configureApiClient` to run after the current test, so no test leaks global state.
- `installFetch`: route-keyed `fetch` stub that records requests.
- `signedInSession` / `signedOutSession`: session states for a preloaded store.
- `renderRouteTree` and `renderWithProviders` take a `transport`, so a test can send API calls to the real mock API (`createMockTransport()` over `localStorage`) or to a canned answer.
- `readSourceFile`: reads a stylesheet for the contract in `theme/components.test.ts`, which asserts the few layout and accessibility rules jsdom cannot measure.

## Database tests

`scripts/db/seed.test.ts` and `scripts/db/isolation.test.ts` run against a scratch database that each file creates on the local Postgres, migrates and seeds (`scratchDatabase.ts`), then drops; they never touch the stack's own data and are skipped, with the token tests, when the stack is not up or `DATABASE_URL` is unset. `seed.test.ts` has three flows: the migrations (every table has RLS and the tenant policy, `anon` and `authenticated` read nothing, the committed Kysely types equal what `db:types` would write), the enum columns (each allows exactly the values the contracts name) and the seed (TEST 6 and DEMO 30 claims, row counts equal to the loader's, the TEST figures of `expected_metrics.json` in SQL, the rule configuration, a quarantined row reported and not inserted, a second run giving the same counts). `isolation.test.ts` has three: a TEST session under RLS sees no DEMO row in any table, cannot write or change one, a session with no tenant sees nothing and a claim cannot reference another tenant's policy (DEMO is given a task and an audit entry so the task tables are not empty), with the same through `withTenant`; and the membership lookup, the audit trail and tasks the application role can never delete, the task counter; and a third test checks that Supabase's REST API answers the anonymous key 401 permission denied on the stack's own migrated database (PostgREST cannot see the scratch one).

## Auth tests

## The local-stack skip

`src/server/tests/unit/platform-auth/verify.local-stack.test.ts` verifies tokens issued by the real local Supabase Auth against its JWKS. It probes `<SUPABASE_URL>/auth/v1/health` once at load and skips the whole file when `.env.local` is missing or the stack does not answer, so `bun run test` passes on a machine without Docker (5 tests skipped, the token test and the four database tests; the database tests skip the same way, probing `DATABASE_URL`). CI starts the stack first, so there they run. Because skipped tests hide regressions, CI runs the unit project through the skip assertion (`ci:test:unit`).

## Count floors

`bun run ci:test:ui` and `ci:test:unit` write a Vitest JSON report and run `scripts/ci/assert-test-run.ts`, which fails when the run did not succeed, when any test failed or was skipped, or when fewer than `--min-tests` tests ran (it catches silently dropped suites). The floors in `package.json` are sized to what exists: SPA 59, unit 32 (the number of unit tests that run with the stack up). Raise them in the same change that adds tests. `ci:test:unit` also fails on the skipped local-stack and database tests, so it is only meaningful where the stack is up, which is where CI runs it, beside `ci:test:ui` for the SPA.

## End-to-end

`e2e_tests/playwright.config.ts` has two projects. `stack` starts Vite itself on `WEB_PORT` (default 5380, strict port, never reusing a server) with the root `.env.local`. `prototype` builds a production build in prototype mode into `src/ui/dist-prototype` and serves it with `vite preview` on `PROTOTYPE_PORT` (default 5381); it needs no stack (`bun run test:e2e:prototype`). `specs/prototype.spec.ts` has one flow at 1366×768 on that build: a deep link meets the sign-in page (banner, roles, no password form), a role click signs in and returns to the link, the six destinations, a claim and its invoices load from the in-browser mock API, a reload keeps the session, persona and theme, sign-out returns to sign-in, every step passes axe, and no request leaves the page's origin. `specs/acceptance.spec.ts` (also in the prototype project) is the acceptance pass: CLM-AT-01 to 16 of the requirements as two flows on the TEST data set, every assertion block a `test.step` named after its scenario. The second flow adds a few test-only fixture rows in the browser (`specs/testOnlyRows.ts` rewrites the script response; `fixtures/v1` is never edited) for the scenarios the shipped data has no row for: a missing stage time, events out of order, pending and rejected payments, and a reopened claim. `docs/acceptance.md` maps each scenario to its step and its earlier unit proof. `specs/support.ts` holds the axe and horizontal-scroll checks the specs share. The stack project's `specs/claims.spec.ts` has one flow at 1366×768: a Head of Claims signs in, selects TEST, reads the Overview figures, reaches a card with the keyboard and opens its claims, filters, downloads the CSV and compares it to the table, reads Stages & Aging, switches the period, reads Exceptions & SLA, opens the flagged claim and its policy's invoices, resets (the toast on screen passes axe) and switches to the dark theme; every step passes axe with no horizontal scroll. `specs/shell.spec.ts` has two flows against the real local stack: the signed-out one (redirect to sign-in, the sign-in page, a wrong password) and the signed-in one (a seeded demo account signs in, walks the six destinations (each with its filter bar), reads a supplier's figures and opens its cases, creates a task in the Action Queue, moves it on, reads its history and finds it again after a reload, opens a claim and its policy's invoices, switches persona and theme and keeps them across a reload, and signs out). It runs axe (WCAG 2.0/2.1 A and AA) on the sign-in page, the signed-in shell and the shell after a reload; any violation fails the test.

Prerequisites: Docker running, `bun run supabase:start`, `.env.local` written, `bun run auth:personas`, and the browser once with `bunx playwright install chromium` (from `e2e_tests`).

## Security scans

`bun run ci:security` runs two scans. `scan-secrets` checks every file git would commit for JWT-shaped strings, Supabase secret keys, private keys and connection URLs with an inline password. `scan-bundle` builds the SPA and fails when `src/ui/dist` contains demo-account e-mails or mock-api source paths (the in-browser mock API itself ships in Stage A), `src/server` code, a server-only variable name, a service-role key, the marker of the development-only demo-accounts quick-pick, or a production Content-Security-Policy with development relaxations. `scan-bundle --prototype` does the same on a prototype build (`src/ui/dist-prototype`) and also fails on supabase-js (its code, a chunk named after it) or a `connect-src` other than `'self'`; `ci:security` runs both, and `scripts/ci/scan-bundle.test.ts` checks that the prototype rules fail where they should.

## CI

`.github/workflows/ci.yml` has one `verify` job on every push and pull request: set up Bun from `.bun-version`, `bun install --frozen-lockfile`, print tool versions, start the local Supabase stack, write a throwaway `.env.local` from `supabase status` (with `DATABASE_URL`), apply the migrations (`db:migrate`), rebuild the database from empty (`db:reset`: migrations, demo accounts, TEST and DEMO seed), then typecheck, typecheck the SPA, lint, lint the SPA (with Prettier), unit tests with the floor (the database tests among them), SPA tests with the floor, the production build, a second build in prototype mode with `.env.local` moved aside (the Vercel build), the security scans, install Chromium, run Playwright, upload the Playwright report on failure and stop the stack. Runs on one ref cancel older ones, except on `main` and `dev`.

`bun run verify` is the local equivalent of the non-browser steps: typecheck, typecheck:ui, lint, lint:ui, test, test:ui, build:ui.

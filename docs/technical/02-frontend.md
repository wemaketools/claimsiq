## Design system

Tokens and classes are the suite's, with the prefix `ciq`. Components use tokens only: no raw hex, no literal pixel gaps (half steps are tokens: `space-0-5`, `space-1-5`, `space-2-5`). The theme is the `data-theme` attribute on `<html>` (`light` or `dark`), set by the auth provider from the session slice and remembered under `ciq.theme`. Text colours on tinted surfaces use the AA `-text` tokens; solid fills use `accent-fill` with `on-solid`.

## Shell

Dark sidebar (tenant label, wordmark, sub-brand, the eight destinations, the user card), a sticky top bar of at least 64px (page title, the data controls, **Viewing as** persona switch, theme toggle; below 768px the data controls wrap onto a second row) and the main region. Below 1280px the sidebar is an icon rail by CSS (DD-64): the sidebar no longer clips there, so the profile menu opens in full over the page, and between 768 and 1279px a "Full sidebar" toggle at the bottom (`aria-expanded`, only rendered in that range, `useMediaQuery(RAIL_QUERY)`) swaps the rail for the full sidebar, which pushes the content (the top bar wraps its data controls below 1200px); the choice is `ciq.sidebar` (`readStoredSidebarExpanded`, anything but "expanded" is collapsed) and `AppShell` adds `ciq-app--sidebar-expanded`; below 768px it is a drawer (closed: hidden from focus; open: focus moves to the first link; Escape or the scrim closes it). Pages put their title in the top bar through `PageHeader`, and their own actions in the page head.

The persona is `session.persona`, written by `choosePersona` (which also stores it) and read once when the store is created. The user card shows the name of the account and the active persona. Each persona has a landing screen (`PERSONA_LANDING` in `personas.ts`, DD-66): `/` is guarded and `LandingRedirect` sends it there (the first destination if the screen is not registered), the top bar's persona switch opens `/`, so `LandingRedirect` is the one place that decides, and `RouteGuard` keeps the requested address for a deep link but not after an explicit sign-out.

## Data controls and context

`session` holds who is signed in; `dataContext` holds the data set (TEST or DEMO, default DEMO) and the as-of date (default 2026-10-21). Both are remembered under `ciq.dataSet` (a prototype build ignores it, DD-66) and `ciq.asOf` and read once when the store is created. The tenant is `tenantOf(dataSet)` (`useTenant()`), and the sidebar label and `X-Tenant-Id` follow it. `chooseDataSet` and `chooseAsOf` store the value, update the slice and make every mounted query read again; `useApiQuery` keys its cached data on data set and as-of date too, so a query never shows the other data set's records while it loads, and a different request (another claim, another policy) shows no data until it answers; only a list filtered in place opts into keeping the previous answer (`keepPrevious`).

`DataControls` (top bar): the data set select (not rendered in a prototype build, which serves DEMO and reads the data set only from `ciq.prototype.dataSet`, DD-66; the e2e helper `selectDataSet` writes that key), the as-of date, "Data issues (n)" (`DataIssuesDialog`, from `data.issues`) and Reset (`ConfirmActionDialog`, then `demo.reset`; the data set and the as-of date stay). Below 1280px their labels are visually hidden, below 768px they wrap onto a second row.

## Feature modules

A feature is `features/<feature>/routes.tsx` exporting `features: FeatureModule[]` (`id`, `routes`, `nav`). The registry collects every such file with `import.meta.glob`, validates it (duplicates and malformed modules are reported with `console.error` and skipped), and both the router and the sidebar are built from the result. Routes are paths in the shell, `load` for a code-split page or `element` for an eager one. Nav items have an id, an i18n label key, a path, an order and an icon. The feature's strings live in `features/<feature>/i18n/en.ts`; its keys are namespaced by the directory name, which must not be one of the shell namespaces.

Routes: `/` is guarded and redirects to the active persona's landing screen, or to the first destination if that screen is not registered; `/signin`, `/forgot-password`, `/reset-password` are outside the shell; every feature route is inside `RouteGuard` and `AppShell`; anything else is Not found (inside the shell when signed in). A route that fails to load or throws renders `RouteErrorPage` inside the shell.

## Claim screens

Overview (`features/overview`), Stages & Aging (`features/stages`) and Claims (`features/claims`) read one engine answer through `features/claim-scope`: `useClaimScope()` returns the shared filters (policy, broker, product, handler, and the period window of the period cards: `filters.byScreen['claim-scope']`, remembered under `ciq.filters`, cleared with the data set and on sign-out; Clear filters keeps the period), the `claims.facts` query for exactly those filters (the answer holds `items`, `summary` with its `period` figures, and the product, broker and handler `breakdowns`) and the master-data lookups (`useClaimLookups`: names for client, product and handler and the filter choices). `ClaimFilterBar` is the one filter bar. `criteria.ts` holds the criterion a figure counts, how it travels in the address (`/claims?show=stage:Assessment`) and the predicate that selects those claims from the facts; `stageAgeRows.ts` makes the stage and age rows from the summary; `ExportCsvButton` downloads the rows a screen builds from its own figures (`lib/csv.ts`) and is off while any of its required `queries` is on its way or has failed; `optionalQueries` are only waited for, so the Action Queue still exports with a dash where the claim facts failed (DD-36, DD-44). Screens never recompute a rule: a figure is a field of the engine's summary, a list is a selection of its facts. `reasons.ts` writes the engine's severity reasons in words (rule, trigger data), `Chips.tsx` and `labels.ts` are the severity and SLA chips, `moment.ts` formats a date or time (a missing one reads "Unknown") and `paths.ts` holds the claim and policy-invoice addresses. Exceptions & SLA (`features/exceptions`) lists the flagged open claims with the shared filters plus severity and reason; Claim Detail reads `claims.get`, `claims.facts` for one `claim_id`, the claim's tasks and the master names. Decisions: DD-28 to DD-39.

Claim Detail's what-if card (`features/claim-detail/WhatIfCard.tsx`, DD-60) reads `claims.whatIf` with the chosen stage kept in component state (keyed on data set, as-of date and claim, so it never survives a change of any of them), and shows the engine's answer for the real and the what-if view side by side; it saves and invalidates nothing.

The Digest (`features/digest`, DD-63) asks the same typed endpoints as the screens it summarises (`claims.facts` through `useClaimScope()`, `suppliers.insights`, `suppliers.list`, `tasks.list`, `users.list`), takes the shared filters and the as-of date, and shows the data set, the as-of date and the filters in its own header, which is what a printout carries. `window.print()` is the Print button; the printed page is the `@media print` block of `theme/components.css`: the shell, the filter bar and every control are hidden (`body:has(.ciq-digest)`, so no other page changes), `@page` is A4 with 7mm margins, the dark tokens sit in `@media not print` so the printout is light whatever the screen theme is, and the tables are compact with the first rows only (5 exceptions, 3 reserve movements, 3 suppliers, 5 actions, each saying "Showing n of m").

Overview's "Paid by month" card (`features/overview/PaidTrendCard.tsx`, `trends.ts`, DD-62) reads `claims.paidTrend` with the shared filters and has its own loading, error and empty states; its months are also rows of the Overview CSV. The Overview's cards are two groups (`FigureGroups.tsx`, `figures.ts`): the as-of group, which includes High-priority exceptions, and the period group (New claims, Paid in period, Average closed turnaround), whose note says it follows the period selector (DD-65). The chart's axis ticks, bar width and one-month line are `GroupedBarChart`'s `evenAxis` and `maxBarSize` props and `PaidTrendCard`. Supplier Insights reads the shared filters through `useClaimScope()` and its own figures from `suppliers.insights`, including the wait percentiles and their baseline (`WaitPercentiles.tsx`: a chart and a table that show a supplier below the sample minimum with its sample and no percentile, DD-62); a supplier opens the Claims list with the `supplier:<id>` criterion (DD-40, DD-41). The Action Queue has its own filters (status, owner, priority), is never limited by persona (DD-43) and shows the engine's `overdue` flag on each task (DD-42); its dialogs, and the same assign and status buttons on Claim Detail's task list, are the ones in `features/claim-tasks`.

## States

Every screen has a loading, an empty and an error state, and a restricted state where a view can be limited. `EmptyState`, `ErrorState` (a 403 renders the restricted state instead) and `RestrictedState` are in `components/ui`; `QueryView` wires a `useApiQuery` result to them.

## API client

`call(endpoint, { params, query, body }, options)` sends the bearer token (read per request from the supabase-js session), `X-Tenant-Id`, `X-As-Of` and `X-Persona` (none of them on `public` endpoints), an `Idempotency-Key` on idempotent commands, normalizes `application/problem+json` to `ApiError`, signs the user out on 401 and, in development builds, parses the response with the endpoint's zod schema so drift fails loudly. The auth provider of the build's mode installs the adapters with `configureApiClient` (a prototype build sends no token), including the `transport` that `main.tsx` passes (the mock API in a prototype build; none otherwise, so the platform `fetch` sends the request to `/api/v1` on the app's own origin, proxied to the API server by Vite in development). The endpoints are the typed contracts of `src/contracts` (`endpoints.claimsList`, `endpoints.tasksCreate`, …); screens call them with `useApiQuery` and `useApiMutation` and never import the mock API.

## Tests

Vitest with jsdom, colocated `*.test.ts(x)`; setup in `test/setup.ts`; helpers in `test/` (`renderWithProviders`, `installFetch`, `signedInSession`). The stylesheet contracts jsdom cannot measure are asserted on the CSS text (`theme/components.test.ts`). The Playwright suite in `e2e_tests/specs` signs in with the seeded accounts and runs axe.
